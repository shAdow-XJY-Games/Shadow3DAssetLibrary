# Gallery development and validation

Public frontend source lives only in `../docs/`. GitHub Pages should publish `main:/docs`; there is no generated duplicate directory, build dependency, workflow requirement, model bundle, Release, or Git LFS usage. `docs/` contains HTML, CSS, ES modules, metadata and `.nojekyll` only. Every thumbnail, GLB, Blender source and generator link is derived from its explicitly allowlisted repository and pinned raw GitHub asset commit.

Run from repository root with Node.js 22 or later:

    node gallery/test.mjs
    node --test gallery/runtime.test.mjs
    node gallery/build.mjs --check
    BASE_REF=<trusted-base-commit> node gallery/build.mjs --check

The last command additionally rejects tracked-file deletion against the base commit. This is a local check, not a branch-protection rule. The publisher must also enforce non-force updates to an expected parent and preserve all tree paths. Optional packaging to a fresh directory is available with `node gallery/build.mjs /tmp/shadow-pages-check`; it copies the checked frontend/metadata allowlist only and never deletes contaminated outputs.

Budgets: public file <=256 KiB; active index plus referenced shards <=1 MiB; retained unreferenced shards plus frozen legacy <=8 MiB (75% warning); runtime/page shell <=256 KiB; total local package <=9.25 MiB; GLB <=5 MiB; image <=2 MiB; Python generator <=512 KiB; Blender file <=25 MiB; <=100,000 triangles and <=64 materials per catalog asset. Checks verify actual file sizes and SHA-256 against metadata. An empty catalog is supported and does not claim any completed assets.

Preview locally with `python -m http.server 8080 --directory docs`. Three.js 0.180.0 and its official addon modules load lazily from the pinned jsDelivr npm version only when the visitor opens the 3D preview. No npm install is needed. Catalog browsing and renders do not require Three.js. A CDN failure is shown as a recoverable preview error; downloads remain available. GLBs must be self-contained; external model subresources are rejected. The Three.js dependency retains its upstream MIT license; it does not license project source, models or artwork.

Manual browser QA still required: desktop/mobile layout, filter/reset, repeated open/close and rapid mode changes, Escape dismissal, WebGL rendering/orbit/zoom/reset, actual immutable raw downloads, unavailable reference state, failed network state, keyboard focus. Node tests alone do not validate visual appearance or WebGL.

All original project source, models and artwork: All rights reserved. Public visibility and download access are not an open-source or asset reuse license. Obtain separate permission before reuse.

## Local-only runtime regression tests

`gallery/runtime.test.mjs` uses a minimal DOM test double, not a browser. It creates a visibly labeled synthetic catalog only under the OS temporary directory, never in `docs/`, and mocks catalog HTTP. Coverage includes empty/error states, filters/reset, detail open/close, safe text rendering, immutable download URLs, missing references, stale image errors, metadata rejection, and GLB CORS request options/hash/size/cancellation failures. This does not prove browser rendering, live GitHub CORS response headers or actual WebGL behavior.

The 3D viewer fetches GLB with `mode: cors`, no credentials and no redirects, a 30-second timeout, a metadata size bound, and an actual SHA-256 comparison before parsing. Switching views or closing cancels the pending fetch. Browser SHA-256 requires HTTPS or localhost. Thumbnail images and direct download links are pinned to commits but are not fetched and hash-verified by this runtime; metadata shows their expected hashes. No token, CORS proxy or authentication workaround is used.

## Metadata v2 compatibility migration

This is a bounded first step, not unlimited scaling. `docs/catalog.json` stays v1 permanently as a frozen migration snapshot. New runtime requests `catalog-v2.json` first and falls back to v1 ONLY for HTTP 404, never for HTTP/network/integrity errors. Runtime accepts v1 or v2; v2 is an index with `{schemaVersion:2, collection, source?, sources?, assetCount, shards:[{theme,count,path,size,sha256}]}`. Each shard is `{schemaVersion:2,theme,assets}`; assets retain the existing v1 record and immutable source references unchanged. Index source maps are authoritative. Paths must exactly equal `metadata/<full SHA-256>.json`, with no arbitrary URLs. Multiple bounded shards may share a theme. Before fetching, the runtime rejects more than 256 shards, an encoded index over 256 KiB, or index plus declared shard bytes over 1 MiB. Both v2 entry and v1 fallback stream at most 256 KiB of actual decoded response bytes before JSON.parse, under a shared 30-second timeout. Whitespace inflation is bounded before parsing; stalled bodies are canceled. The actual entry byte count also participates in the aggregate metadata check. The dedicated metadata reader hashes browser-decoded bytes: gzip/br Content-Length is compressed transport length and is not compared with decoded metadata size; identity Content-Length is checked when present. Streamed decoded bytes are bounded and final size/hash always verified. Existing GLB reader behavior is unchanged. Actual response sizes/hashes remain enforced per shard; complete Pages checks additionally count runtime, legacy snapshot and retained shards. All records must have globally unique IDs.

Run `node --test gallery/metadata.test.mjs gallery/metadata-network.test.mjs gallery/packaging-v2.test.mjs gallery/budget.test.mjs` in addition to the existing checks. Convert a frozen v1 candidate offline with `node gallery/shard-catalog.mjs <latest-input-v1.json> <new-output-directory> [frozen-legacy-v1.json] [retained-shards-directory]`. The converter refuses oversized indices/records and reports separately the unchanged 1 MiB active metadata budget, 8 MiB archival budget (legacy plus unreferenced shards), and 256 KiB runtime/shell budget. It measures retained files from docs/metadata by default (directory overridable), and warns at 75% of the archival budget. These are local project limits, not hosting-provider limits. It never modifies its input, asset pins or existing output. The publisher must combine metadata with runtime and run `build.mjs --check`; classification uses exact references in the current index; history, active metadata and shell each have their own enforced cap, and the package cap is their sum.

Two-stage rollout:
1. Publish reviewed app and new core-catalog-v2.mjs module (which imports only established core.mjs exports) and validation tooling while keeping the latest v1 catalog unchanged. Verify live v1 behavior before any v2 index.
2. Regenerate v2 metadata from the latest approved catalog AT PUBLICATION TIME, verify every asset/pin against v1, publish hash-named shards and catalog-v2.json in the same commit, and verify Pages serves those exact bytes. Keep catalog.json as the migration-time v1 snapshot; older cached clients remain functional on that snapshot and need a refresh/new runtime to see subsequent additions. Do not claim immediate complete results on every cached client. Never replace a named shard with different bytes. Keep prior hash shards and their source IDs while old indices may be cached. Build accepts retained shards only when names match their actual SHA-256, records validate, and total budgets still pass. Retention is not free and must be included in capacity planning. No asset binaries/renders are placed in Pages. This worker does not publish.

The unchanged UI initially loads ALL metadata (up to four shard requests concurrently), hashes and validates it, then renders and populates complete filters. Search includes id/title/description/category/theme/style and retains all existing facets. Loading and failure are explicit; no partial result is presented as a whole-library search. The store's theme-scoped API loads only matching shards, but the current UI intentionally uses the global mode. Verified shards are cached only after a complete successful request; retries are safe. Caller cancellation, 30-second timeout, malformed JSON, wrong sizes/hashes, cross-shard duplicates and unapproved sources reject the request; sibling requests are canceled on failure.

100-asset measured snapshot: v1 catalog 161,520 bytes; v2 index 4,269 bytes + 10 shards 120,060 bytes = 124,329 metadata bytes. Complete cache-safe v2 Pages package including legacy v1 and runtime 318,209 bytes at measurement. Default v2 first load: 11 metadata HTTP requests; runtime-first v1 fallback makes 2 requests; no claim of lazy first-load savings. Global search after initial loading is local, with no additional metadata requests. A theme-scoped consumer pays index plus only that theme's shards, but must not label those partial data global.

At similar density, 145 assets are roughly 180 KB v2 metadata plus runtime and the retained legacy v1 snapshot (estimate, not a validation of unpublished assets). The 256 KiB per-file budget is preserved by splitting large themes; the unchanged 1 MiB actively loaded metadata cap bounds library size; retained history no longer reduces that client loading budget and is separately capped at 8 MiB. Before approaching the warning: introduce a separately hash-pinned compact summary/search index with every field needed for exact global search, render paginated result cards and fetch full records only for selected pages/details. Version and verify the summary-to-record link. If that summary itself grows too large, design a bounded server/search solution or separately review budget changes; do not silently raise limits or claim unloaded data were searched.

Node checks cover state and integrity, not a real browser or WebGL. Existing browser/manual checks remain required after publication.


## Paged catalog v3 (long-term on-demand path)

`index.html` loads the separately named `app-v3.mjs`; the original `app.mjs`, `core-catalog-v2.mjs`, `catalog.json`, `catalog-v2.json` and all old `docs/metadata/` files stay unchanged at migration. Cached old HTML therefore continues to use its original v1/v2 application and migration snapshot. It will not automatically see v3 additions. The new reader requests `catalog-v3.json` and falls back to v2/v1 only on HTTP 404, with a visible historical-compatibility notice. Network, authorization, format and integrity errors never silently substitute an older catalog.

### Bounded data model and transport

The v3 root has only collection metadata, total asset count, a snapshot digest, one explicitly allowlisted immutable metadata repository/commit, and four tree descriptors: records, terms, facets, and sources. Root bytes are capped at 16 KiB. It contains neither every shard nor a growing source map. Tree nodes live outside Pages at `catalog/v3/<hash-prefix>/<full-sha256>.json`. The root pins the Git commit that already contains the entire graph. Requests use raw GitHub with CORS, no credentials and no redirects, with no user-selected hostname or path. Original asset IDs, records, ordering, source IDs, asset commit pins and role paths do not change.

All graph objects are content addressed, byte-counted and SHA-256 checked before use. A small fanout (32) and bounded leaves provide logarithmic navigation; height is capped at 12 as a corruption/work bound. Full records are grouped in original-order pages of at most 24 records, with only their required source mappings. Source, term and facet dictionaries use compressed binary UTF-16 radix buckets with small branch levels folded so insertion changes only the affected bucket/ancestors instead of shifting all later dictionary pages. Branch children may have different heights, but every edge strictly decreases height. A separately paginated source tree retains complete provenance for offline reconstruction without loading all sources in the browser. Branch count/range/height and per-family payloads are validated. The publisher additionally reconstructs the whole graph, checks globally unique IDs, and regenerates every search/facet tree to prove completeness. A browser cannot independently prove global ID uniqueness without downloading the entire library; it instead verifies the immutable audited graph and detects duplicate IDs in each result page.

Theme, type, category, style and repository facets have exact global posting lists. Search preserves the previous case-insensitive trimmed substring semantics over id/title/description/category/theme/style (not a new tags field). Unicode 1/2/3-gram postings select candidates, at most eight necessary query grams are intersected, and the full original string is always checked before returning a record. Short postings are embedded in bounded dictionary leaves; long lists are separately paged. This avoids thousands of tiny per-term files and does not require a global summary download. Original record order is the stable result order. No asset is rotated out or hidden to meet a budget.

Runtime bounds: decoded node <=256 KiB; target generated record/source/facet/posting node <=48 KiB except a single larger valid record; dense term leaves <=1,024 entries and target <=96 KiB; root <=16 KiB; one query <=1 MiB reserved decoded fetch bytes and <=96 requests including retries; the complete initial bootstrap shares that same budget across the actual root bytes, first record page and all five selector first batches; global store concurrency <=4; 30-second operation deadline; at most two retries for transient network/HTTP failures, never for invalid hashes/JSON. An LRU retains <=2 MiB encoded-equivalent metadata and <=128 nodes (JavaScript object overhead is additional, not claimed to equal encoded bytes). A selector that cannot finish inside this shared startup budget exposes an explicit load/retry button, with no automatic fresh-budget continuation. Concurrent requests for the same uncached node are not coalesced: each attempt is conservatively charged to its operation, subject to the global concurrency/queue bounds. Only fully decoded, hash- and schema-verified nodes enter the cache; failed/incomplete responses never do. Cards are limited to 24. Every operation has a finite candidate/seek budget. A work/byte-limited search returns an explicit continuation rather than pretending its prefix was the entire library. Cancellation or a network/integrity failure returns no partial result; individually verified immutable cache nodes remain reusable. Back navigation reuses verified cache entries when still resident.

The library total and individual facet counts are exact. Unfiltered and single-facet/short-single-gram counts are exact without scanning records. For more complex intersections/long substring search, the UI explicitly states that the total is not yet complete; it never labels the current page or loaded subset a full-library match count. Following all continuation pages produces the exact total and complete results, including late matches. There is no unbounded hidden background count/download. Facet option lists also paginate (24 values per batch); “more options” reaches every value. Search/reset cancels obsolete queries, and a failed page has a retry path that retains navigation history.

### Publication and subsequent asset additions

Do not run the old v2 publisher after switching the active app to v3. Its exact-seven-blob, last-two-files and one-added-restored-file assumptions are intentionally not reused. `publish-catalog-v3.mjs` is an offline adapter for the sole writer; it performs no Git/network writes.

1. At the maintenance boundary, re-read the actual main commit, complete tree and canonical full catalog. Never publish an earlier 463/464/465 test snapshot over newer assets. For a normal append, first publish/create the already approved asset blobs in an immutable asset commit using the existing asset-file/schema/freeze checks. Construct the new record's unique source ID with that verified asset commit. `node gallery/publish-catalog-v3.mjs from-approved <approved-core-files.json> <source-id> <verified-asset-commit> <addition-output>` rechecks the exact existing five-file freeze (bytes, SHA-256, Git blob IDs and record-role mappings) and produces the addition without hand-editing metadata.
2. Run `node gallery/publish-catalog-v3.mjs prepare <latest-expanded-v1> <complete-current-tree> <fresh-output> [approved-addition.json]`. An addition is `{assets:[record], sources:{sourceId:{owner,repo,commit}}}`. The adapter refuses replacement IDs/source pins, proves every old record/order/role URL unchanged, rebuilds exact indexes, checks the 256 MiB offline graph budget, and emits an explicit delta for only absent content-addressed graph paths. Existing graph paths must have exactly matching Git blob IDs and sizes. It also records every protected legacy path.
3. The sole writer creates graph blobs/tree/commit on the verified preceding commit, retaining all prior paths. Check the graph-stage tree with `verifyExactTreeChanges`, and every active node (including reused nodes) with `verifyRemoteGraphTree` against the complete immutable Git tree. Check the commit parent. Graph data is still invisible to the active old root at this point.
4. Run `node gallery/publish-catalog-v3.mjs entry <prepared-output> <verified-graph-commit>` to generate `catalog-v3.json` and its exact one-file entry manifest. Initial migration combines this with the separately reviewed runtime/UI/schema/tool manifest. Normal later additions change only the new graph delta and this root, in addition to their approved core asset files. Old v1/v2 files and all prior graph files remain byte-identical.
5. Create the entry commit on the graph commit. `verifyCommitChain` requires baseline -> asset (append only) -> graph -> entry and verifies the root pins that exact graph commit. Use explicit stage manifests with `verifyExactTreeChanges`; never infer stages from list tails or loosen path allowlists. Recheck main and perform one expected-parent, non-force CAS. If main moved, do not overwrite; rebuild from the new canonical catalog. Journaling, uncertain-result reconciliation and successful-CAS accounting remain mandatory sole-writer responsibilities.
6. Postcheck the final ref/entry commit, immutable root blob, all active graph blob identities and unchanged legacy/core tree paths. Do not mark complete solely because local tests pass. No browser or deployed-site check is claimed by these offline tools.

For a future append, the canonical full input can be recovered locally from the exact pinned graph with `node gallery/catalog-v3.mjs expand <entry> <repository-root> <output-v1>`. `catalog-v3.mjs prepare/pin/audit` also provide deterministic standalone graph generation and full offline audit. Source data and graph paths are append-only; no cleanup/deletion is performed. History remains readable at pinned commits. Git storage still has a real cost: the active graph has an explicit 256 MiB local audit cap (50k synthetic assets measured below it), and retained graph history must be capacity-planned separately. This is not a claim of unlimited repository/hosting capacity.

### Packaging and validation scope

Pages keeps the unchanged old <=1 MiB v2 active limit when serving v2. With v3 active, its tiny root is active metadata; frozen v1/v2 indices and old shards use the existing <=8 MiB history budget, and runtime/shell stays <=256 KiB. The old total Pages package ceiling stays 9.25 MiB. The growing v3 graph is not copied into Pages at all. The offline 256 MiB graph cap is a separate storage/audit guard, not an increase to the browser's old full-download budget.

Run (Node 22+):

    node --test gallery/runtime.test.mjs gallery/metadata.test.mjs gallery/metadata-network.test.mjs gallery/budget.test.mjs gallery/packaging-v2.test.mjs
    node --test gallery/catalog-v3.test.mjs gallery/catalog-v3-network.test.mjs gallery/runtime-v3.test.mjs gallery/publish-catalog-v3.test.mjs gallery/packaging-v3.test.mjs
    SCALE_REPORT=/tmp/catalog-v3-scale.json node --max-old-space-size=4096 gallery/catalog-v3-scale.mjs
    node gallery/build.mjs --check

The last command requires all actual pinned asset binaries and every retained historical file locally, as before. Do not claim a full real-data binary build from a metadata-only handoff. Synthetic packaging tests exercise the full allowlist/build without fabricating published assets. DOM tests are test doubles; they do not validate browser layout, actual external CORS/CDN availability or WebGL. Existing manual browser QA remains a separately scoped step.

Local synthetic scaling (each asset has its own source pin; metadata only): 10,000 assets, root 1,372 B, startup 52,360 B / 8 metadata requests; 50,000 assets, root 1,372 B, startup 57,285 B / 9 requests. Startup includes the first 24 records and first batch of all five facet selectors. The full 50k offline graph is 87,321,498 B, which is never downloaded on startup. Late-record search and combined-filter results were compared against exhaustive reference data; per-operation budgets remain enforced. These figures exclude JavaScript/CSS, thumbnails and network compression, and are not production latency benchmarks.

Publication cost was also measured on real additions: 465→466 emits34 new graph nodes (28 reused); 466→467 emits35 (27 reused). These are metadata index nodes, not additional assets. Initial467 migration has62 graph nodes. The binary radix dictionaries avoid global leaf-position shifts while denser term pages keep ordinary Git blob creation bounded in practice; exact per-publication manifests still govern variable delta sizes.
